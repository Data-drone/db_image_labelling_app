# Image Labelling App Roadmap

**Created:** 2026-04-27
**Last reconciled:** 2026-10-15
**Status:** Living roadmap — implementation status checked against the current repository

Status legend: **✅ Shipped** · **🟡 Partial** · **⬜ Planned**

---

## Current State

The app is deployed as a Databricks App and currently supports:

- Multi-label classification, bounding-box detection, and freeform segmentation
- UC Volume and Delta-table image sources
- Correction history, keyboard workflows, gallery filters, and progress analytics
- Model-assisted pre-labeling, embeddings, similarity tools, and active-learning queues
- JSONL/COCO import and lightweight or copied training-dataset exports
- Optional labeled Delta publication for table-backed projects
- Dataset history and Databricks finetuning Job handoff
- Project cloning/versioning and Databricks SSO identity
- Lakebase as the primary metadata store, with explicit SQLite local development

The main remaining gaps are collaborative workflow controls (locking,
assignment, consensus, and RBAC), additional interchange formats, recursive
Volume scans, and the planned annotation types listed below.

## Phase 2 — Quality of Life

Highest impact, lowest effort. Addresses daily friction for labellers.

### 2.1 Undo / Correction Workflow

**✅ Shipped.** Labellers can revisit and replace labels; create/update/delete
history is retained in `annotation_history` and exposed in the labeling UI.

### 2.2 Keyboard-Driven Workflow for Detection

**✅ Shipped.** Detection and segmentation provide class, navigation, drawing,
and undo/redo shortcuts.

### 2.3 Multi-Label Classification

**✅ Shipped.** Classification saves multiple class annotations per sample.

### 2.4 Progress Dashboard

**✅ Shipped.**

Per-project view showing:
- Total samples, labelled / unlabeled / skipped counts
- Labels per class (bar chart)
- Labelling velocity over time
- Estimated time to completion

### 2.5 Search & Filter in Gallery

**✅ Shipped.** The paginated gallery filters by status, class label, filename,
and labeller.

## Phase 3 — Collaboration & Data Quality

Support multiple concurrent labellers with quality controls.

### 3.1 Collaborative Locking

**🟡 Partial — [#33](https://github.com/Data-drone/db_image_labelling_app/issues/33).**
The backend has lock fields, expiry, and a lock-on-open `/next` endpoint, but
the frontend scrubber bypasses it. Atomic acquisition, ownership checks,
heartbeat, explicit release, and conflict UX remain.

### 3.2 Labeller Assignment & Workload Splitting

**⬜ Planned.** Assign subsets of images to specific labellers so work is
distributed without overlap.

### 3.3 Inter-Annotator Agreement / Review Mode

**✅ Shipped for image classification, detection, and segmentation —
[#38](https://github.com/Data-drone/db_image_labelling_app/issues/38).**
Projects can opt into blind immutable votes with configurable panel size,
coverage, quorum, IoU, and agreement thresholds. Classification uses exact
label-set voting; boxes and masks use deterministic same-class IoU clustering
and submitted medoid geometry. Ambiguous, unmatched, tied, and below-threshold
cases enter an audited visual reviewer queue. Dashboards and exports include
sample- and object-level agreement provenance. Weighted voting, per-class
thresholds, gold items, kappa, and video/track/keypoint/attribute consensus
remain planned.

### 3.4 Role-Based Access

**🟡 Partial.** `ADMIN_EMAILS` protects destructive Admin mutations. Consensus
settings are restricted to the project creator and consensus review uses a
project reviewer allowlist, but there is no general project-level RBAC.
Browsing and non-consensus annotation remain available to anyone with App
access.

Distinguish between:
- **Labeller** — can only label assigned images
- **Reviewer** — can approve/reject labels
- **Project Owner** — can create/configure/export projects

Prevents accidental project deletion or misconfiguration.

### 3.5 Comments / Flags on Samples

**⬜ Planned.** There is no sample comment or ambiguity-flag workflow.

## Phase 4 — Annotation Capabilities

Expand the types of labels the app supports.

### 4.1 Polygon / Freeform Segmentation

**✅ Shipped — [#28](https://github.com/Data-drone/db_image_labelling_app/issues/28).**
Segmentation projects support brush, eraser, polygon, undo/redo, zoom/pan,
brightness/contrast, COCO RLE storage/import/export, and mask PNG export.

### 4.2 Keypoint Annotation

**⬜ Planned.** Keypoint/landmark annotation is not implemented.

### 4.3 Image-Level Attributes / Metadata

**⬜ Planned.** Project source metadata is supported, but editable structured
attributes per image are not.

### 4.4 Model-Assisted Labelling (Pre-Labels)

**✅ Shipped.** Model Serving can create draft labels synchronously or through
a Databricks Job. Humans can review, accept, clear, or correct drafts.

### 4.5 Recursive Volume Scanning

**⬜ Planned.** UC Volume scans remain one level. Delta-table image sources can
reference nested paths but do not make Volume scanning recursive.

## Phase 5 — Import, Export & Integration

Smooth data flow in and out of the app.

### 5.1 Import Existing Labels

**🟡 Partial.** The API supports JSONL and COCO, including COCO polygons and
RLE masks. There is no import UI; Pascal VOC, YOLO text, and CSV import remain
planned.

### 5.2 YOLO Export Format

**⬜ Planned.** Detection exports support reference and copied COCO, not YOLO.

### 5.3 Delta / Lakehouse Sync as First-Class Export

**🟡 Partial.** Tables are Lakehouse Sync-compatible. Dataset export from a
Delta-table source also attempts to publish a labeled Delta snapshot with
lineage through the configured SQL warehouse. A continuously managed sync or
general-purpose Delta export workflow is not built into the App.

### 5.4 Webhook / Notification on Project Completion

**⬜ Planned.** Job handoff is user-triggered; project completion does not emit
a webhook or automatically launch a workflow.

### 5.5 Delta Table as Image Source

**✅ Shipped.**

Create a labeling project from a Unity Catalog Delta table (`image_path` + metadata) instead of (or as well as) listing a UC Volume folder. **Per project:** each project stores its own `source_table` FQN, path column, and optional SQL filter. Bytes still load via the Files API from `/Volumes/...` paths; the table is only the sample catalog.

Intended workflow: images land in a volume → Auto Loader writes/updates the Delta catalog → the app reads that table → **Actions → Sync new table rows** picks up new Auto Loader files without wiping labels. `dbfs:/Volumes/...` paths are normalized to `/Volumes/...`.

Supports nested layouts and extra attributes that one-level volume scan cannot.
Reference exports from table-backed projects attempt to publish a labeled
Delta snapshot and record its lineage in export metadata.

- Implementation plan: [2026-09-28-delta-table-image-source.md](2026-09-28-delta-table-image-source.md)

## Phase 6 — Scale & Advanced UX

For larger teams and datasets.

### 6.1 Active Learning Loop

**✅ Shipped.** Smart Queue supports uncertainty-based active learning with a
diversity-only fallback, backed by pre-label confidence and image embeddings.

### 6.2 Batch Operations

**🟡 Partial.** Bulk accept/clear of model drafts and label propagation are
available. General gallery selection with batch label, skip, or delete is not.

### 6.3 Video Frame Extraction

**⬜ Planned.** Video ingestion and frame extraction are not implemented.

### 6.4 Dark Mode / Accessibility

**🟡 Partial.** The app uses a dark visual theme and labeling has substantial
keyboard support. A complete screen-reader, focus-management, and WCAG audit
has not been completed.

### 6.5 Audit Log

**🟡 Partial.** Annotation create/update/delete history records identity,
timestamps, and prior/new annotation state. There is no app-wide audit log for
project, export, import, Admin, or Job actions.
